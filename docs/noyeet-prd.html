Product requirements & system architecture

noyeet

Your agent can't yeet your money. Agents don't get keys. They get permits — and the permit is decided by what the chain says will happen, then enforced atomically when it does.

01Problem

An autonomous agent holding a private key is an unbounded liability. It decides, it signs, it broadcasts — and nothing between those three steps can tell it no.

Two failures are structural, not incidental, and neither is solved by better prompting.

Nothing stops a bad transaction before it lands. Prompt injection, a hallucinated address, a decimals error, a stale oracle read. The model decides and the transaction is irreversible. Existing guardrails — Turnkey policies, Safe module roles, session-key permissions — all evaluate calldata. Calldata is what the agent claims it will do. It is not what will happen.

Nothing proves what happened afterward. "The agent only rebalances below a 1.4 health factor." Prove it. Logs are self-reported, mutable, and stored by the party who would need to be lying. There is no receipt an outside party can check.

KeeperHub already solved landing the transaction — gas estimation, retries, nonce management, private routing. The open problem sits one step earlier and one step later: authorizing the transaction against its real consequences, and proving the decision afterward.

02Thesis

Simulation is available before broadcast. KeeperHub's simulate: true returns a gas estimate and a revert flag — but no state diff, so post-state cannot be read directly.

So invert it. Express every invariant as a revert condition inside the transaction itself. A guard contract executes the agent's calls, then asserts post-state and reverts if any invariant is broken. Run that composite through simulation: a revert means the future is bad, and the transaction is denied before it exists. Run the same composite for real, and the identical assertion enforces on-chain — so if state moves between simulation and inclusion, the transaction reverts instead of doing damage.

Prediction and enforcement become the same object. That is the primitive.

The consequence: noyeet expresses policies no calldata-level system can. Deny if this transaction drops my health factor below 1.4. Deny if realized slippage exceeds 2%, measured from chain state rather than from the agent's claim. Deny if actual gas exceeds the estimate by more than 3×.

03Goals and non-goals

Goals

  • Any agent framework executes onchain without ever holding a key.
  • Every execution is gated on simulated consequence, not just calldata shape.
  • Every decision — including refusals — produces a receipt a third party can verify.
  • Ambiguous actions escalate to a human instead of failing closed or open.
  • A new builder reaches their first guarded, landed transaction in one command.

Non-goals

  • Not an agent framework. noyeet has no opinion on how the agent reasons.
  • Not a wallet. Keys live in KeeperHub's Turnkey enclaves; noyeet never touches key material.
  • Not a strategy. It does not decide what to do, only whether what was decided is allowed.
  • Not an LLM in the decision path. The model is the untrusted input. Every rule is deterministic.
  • Not a replacement for KeeperHub. It is the authorization and proof layer on top of it.

05The verdict model

Two-state authorization forces a bad tradeoff: strict policy blocks legitimate work, loose policy admits attacks. noyeet has three states, and the third is where real deployments live.

ALLOW

Static rules pass, simulation passes, invariants hold. Executes through KeeperHub with retry and gas management. Receipt anchored in the next batch.

HOLD

Legal but unusual — size, novel counterparty, first use of a selector. Signed and held via Tempo, owner notified with the simulated outcome attached. Released on approval, cancelled on timeout.

DENY

A rule failed or the guard reverted in simulation. No broadcast. The refusal is itself anchored — a blocked attack becomes permanent evidence.

HOLD is what makes the system deployable. The agent keeps moving on everything routine; anything unusual lands in a human's inbox with the consequence already computed, not a raw hex blob to squint at.

07The guard contract

The whole thesis compiles down to one contract. It is deliberately small, immutable, and has no owner beyond an executor allowlist.

struct Call      { address target; uint256 value; bytes data; }
struct Invariant {
    address target;      // contract to read after execution
    bytes   probe;       // staticcall calldata, e.g. getUserAccountData(addr)
    uint8   word;        // which returned word to compare
    Op      op;          // GTE | LTE | EQ | REL_DEC_MAX | REL_INC_MAX
    uint256 threshold;   // absolute bound, or max delta for REL_*
}

error InvariantBroken(uint256 index, uint256 got, uint256 want);
error ProbeFailed(uint256 index);

function executeGuarded(Call[] calldata calls, Invariant[] calldata inv)
    external
    onlyExecutor
    returns (bytes[] memory results)
{
    uint256[] memory before = _snapshot(inv);   // for relative bounds
    results = _execute(calls);                  // the agent's intent
    _assert(inv, before);                       // reverts on violation
    emit Guarded(keccak256(abi.encode(calls)), inv.length);
}

Simulation and execution call the same function with the same arguments. There is no separate "check mode" that could drift from the enforcement path — a class of bug this design cannot have.

Open technical risk — resolve in hour one

If simulate: true returns only a boolean without custom-error data, the violated invariant cannot be named from a single simulation. Fallback: run one probe simulation per invariant in parallel; the reverting probe identifies the violation. This costs latency, not correctness, and changes nothing structural. Cap invariants at four per intent if probe latency proves material.

Receipts are canonicalized with JCS before hashing, so any implementation reproduces the same digest. The verifier is stateless: recompute, prove, compare against the on-chain root.

10Stack

Chosen for a system whose failure mode is losing someone's money: deterministic core, boring dependencies, everything on the decision path testable without a network.

Runtime
Bun + TypeScript, strict
One toolchain for run, test, and bundle. No any permitted on the decision path.
API
Hono
Small, typed, edge-portable. REST, MCP transport, and webhook triggers share one router.
Contracts
Foundry, Solidity 0.8.26
Invariant fuzzing is the whole test strategy for the guard. forge verify runs in the pipeline.
Chain client
viem
Typed ABI encoding and precise revert-data decoding, which the preflight path depends on.
Schema
Zod + JCS canonicalization
Policies and intents validate at the boundary; canonical JSON makes receipt hashes reproducible.
Store
Postgres (Neon) + Drizzle
Receipts are append-only with a hash chain. Database branching gives every pull request real data.
Queue
Postgres-backed job table
One durable store, no Redis to lose. Serialized sends per wallet kill nonce races by construction.
Execution
KeeperHub MCP + CLI
Gas estimation, retry, nonce, Turnkey custody, sponsored gas. noyeet signs nothing itself.
Dashboard
Next.js, React server components
Operator surface and public verifier. The verifier ships static — it must outlive the service.
Telemetry
OpenTelemetry -> Grafana
One trace spans intent, policy, simulation, execution, anchor. The trace ID appears on every receipt.
Tests
Vitest, Foundry, Playwright
Rule-level units, contract fuzzing, and one CI job that lands a real Sepolia transaction.
Delivery
Turborepo, GitHub Actions, Fly.io
Typecheck, test, fuzz, deploy, verify, ship. Preview environment per pull request.

12Threat model

AdversaryCapabilityMitigation
Compromised agentSubmits arbitrary intents with convincing rationaleRationale is metadata, never an input to the decision. The policy VM ignores it entirely
Prompt injection via data sourceSteers the agent toward an attacker addressRecipient allowlist plus invariants on resulting balances — the address is checked and the outcome is checked
Oracle manipulationPoisons one price feedMedian of three with a deviation bound; a single outlier cannot move the decision
MEV, sandwich between simulate and inclusionMoves state after the checkThe guard asserts at inclusion; the transaction reverts rather than executing at a bad price
Operator retroactively edits policyClaims a different rule was in forcePolicy hash committed onchain before the run; changes pass a timelocked workflow
Operator falsifies logsFabricates or deletes a receiptAnchored hashes — a receipt absent from the on-chain root did not exist when claimed
Malicious executor keyCalls the guard directlyExecutor allowlist, and invariants still assert — a rogue executor cannot break the bounds either

The residual trust assumption is stated plainly: noyeet cannot force an agent to route through it. It replaces key custody with permit issuance, so an agent that never held a key has no path around the guard. That is the entire security argument, and it is worth more than any list of rules.

14Success metrics

  • Executions. Guarded transactions landed through KeeperHub, counted live and publicly.
  • Refusals with teeth. Denials where simulation proved a real invariant break — the number showing the gate is load-bearing rather than decorative.
  • Zero false-allows. No transaction that passed noyeet broke an invariant on-chain.
  • External adoption. Agents outside this project routing intents through noyeet/verify and paying for it.
  • Time to first guarded transaction. Measured on a clean machine, target under five minutes.

15Open questions

  • Does simulate: true surface custom-error data? Decides single-simulation versus per-invariant probes. Resolve first.
  • What is the practical ceiling on invariants per intent before preflight latency breaches the 2.5 s objective?
  • Should invariant sets be reusable, named on-chain objects, so a policy references an audited bundle instead of inlining bounds?
  • Does the guard belong per-user, or as a shared singleton with per-caller executor scoping? Singleton is cheaper and more auditable; per-user isolates blast radius.
  • Do receipts need to be portable across execution layers, or is KeeperHub-anchored sufficient for the foreseeable roadmap?
